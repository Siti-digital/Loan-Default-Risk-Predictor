Does the economy at origination predict who defaults?

We test whether national unemployment, its recent change and inflation, all known when a loan is issued, improve default prediction beyond the borrower's own application. On 283,026 loans from 2015 that the models never saw, they do not: borrower data carry the signal, and adding macro data leaves ranking unchanged and pushes the predicted default rate further from the real one.

01 · QUESTION

What we are predicting, for whom, and when

Banks stress-test loan books against recessions, which assumes the economy affects default. We ask a narrower, testable question: at the moment a loan is issued, does knowing the state of the economy help predict whether that loan will default, once we already know the borrower?

QuestionDo macroeconomic conditions available at origination improve default prediction beyond borrower application data?
One rowOne 36-month LendingClub personal loan, described as it looked on its issue month.
Targetdefault = 1 if the loan ended Charged Off / Default; 0 if Fully Paid. Loans still running are excluded.
Prediction timeThe issue month. Inputs are the application fields plus macro data published before that month (2-month lag).
OutputA probability of default (PD) over the loan's life, not a yes/no label.

Short answer

No measurable improvement. Adding three macro features changes 2015 PR-AUC by −0.0005 and ROC-AUC by −0.0005. Across 2013, 2014 and 2015 the macro terms shift the predicted default rate in the wrong direction (correlation with the borrower model's miss: −0.6).

What this project does not claim

It is a predictive comparison on US data from 2007–2015, one lender, and loans that lender chose to approve. Coefficients describe associations, not causal effects of the economy on any borrower. It says nothing about how a loan behaves if the economy changes after issue; that needs a survival model with time-varying covariates.

03 · PREPROCESSING

Every choice uses only information available at issue

Three kinds of leakage are possible in this problem: future outcomes in the label, future macro data in the features, and test-set statistics in the scaling. Each has a specific guard.

  1. Resolved, matured loans onlyKeep 36-month loans issued up to Dec 2015 with a final status. Loans still running are excluded instead of being labelled "good".
  2. Macro transformations before laggingInflation (12-month % change of CPI) and the 6-month unemployment change are computed on the raw monthly series.
  3. 2-month publication lagEvery macro column is shifted by two months, so a June loan sees April data. US unemployment and CPI for a month are released in the first half of the next month. An assertion checks every row.
  4. One FICO featurefico_avg replaces the low/high bounds, which always differ by 4 points and are perfectly collinear.
  5. Log incomeannual_inc is right-skewed (skew 29 raw vs 0.3 after log1p). On the CV folds the log version raised PR-AUC by +0.002, so we kept it. This was decided before the test set was used.
  6. Impute, scale, encode, all fitted on training rowsMedian imputation (mainly mort_acc, not recorded before 2012), standard scaling, one-hot home_ownership. Each CV fold refits these on its own training window, and the final model refits on 2007–2014.

Leakage checks run in the notebook

  • No post-origination columns in any feature set.
  • Target is strictly 0/1 with no missing values; no duplicate rows.
  • Every loan's macro reference month is at least 2 months before its issue month.
  • Train ends Dec 2014, test begins Jan 2015.
  • Scalers and imputers are fitted on training rows only; test rows are only transformed.

Why logistic regression

The objective is log-loss, so the outputs are probabilities on the real default-rate scale. Coefficients are readable as odds ratios, and the model is a closed formula that runs in the browser explorer below. Assumptions: log-odds are additive in the features, and rows are independent. The second assumption fails for macro features, so the statistical model uses standard errors clustered by month.

Why also LightGBM

A linear model could miss a macro effect that only matters past a threshold or for certain borrowers. Gradient-boosted trees can find those shapes without us specifying them, so D vs D-base repeats the B vs C test without the linearity assumption.

Why no class re-weighting

Defaults are about 13–15% of loans. class_weight="balanced" would push predicted PDs toward 50% and wreck calibration. We checked: it lifts the mean 2015 PD to 48% and nearly doubles the Brier score (0.236) with no ranking gain.

Metrics and why

PR-AUC primaryArea under precision–recall. Focuses on the default class; a no-skill model scores the default rate (~0.15), so lift is easy to read.
ROC-AUCChance a random defaulter is ranked above a random payer. Insensitive to the base rate, so it is comparable across years.
Brier scoreMean squared error of the probabilities. Rewards both ranking and correct level.
Mean PD vs actualCalibration-in-the-large: is the predicted portfolio default rate right? This is what loss provisions depend on.
Confusion matrixAt a threshold equal to the training default rate (13.2%), fixed in advance. Accuracy is not reported: predicting "no default" for everyone already scores 85%.

Uncertainty

The B-vs-C differences are bootstrapped by resampling whole issue months (500 draws), because all loans in a month share one macro value. 2015 has only 12 months, so these intervals are rough. They are a sanity check, not a formal test.

Reading the coefficients

  • FICO dominates: one SD higher (~31 points) multiplies the odds of default by 0.67.
  • Income, DTI, loan size, mortgages follow, all in the expected direction.
  • Macro terms are small (odds ratios 0.97–1.08) even where their intervals exclude 1.
  • Unemployment has a negative sign: loans issued when unemployment was high defaulted less. A plausible reading is that LendingClub tightened approvals during and after the recession, so the macro term partly measures who was approved, not how the economy affects a given borrower. The data cannot separate these explanations.
  • With 88 monthly clusters and only one macro value per month, statistical significance here does not mean predictive usefulness. The out-of-time tests above are the evidence that counts.

08 · LIMITATIONS

What these results cannot tell us

The negative finding is specific to this setting. These are the main reasons it might not generalise.

Very few independent macro observations

Training has 88 issue months and the test year has 12. A macro effect has to be learned from 88 data points, however many loans there are.

A calm test year

2015 unemployment moved within about one point, with no recession. Macro data might matter in a downturn, which this test cannot show.

Only approved loans

LendingClub's approval rules changed over the cycle. The macro coefficients mix the economy with who was let in (selection bias).

Macro at origination only

Defaults happen up to 3 years after issue. The economy during repayment is not used, so this is not a full stress test. That would need a hazard model with time-varying covariates.

National series, local borrowers

State-level unemployment (via addr_state) would add variation within a month. It was not used here and is the most promising extension.

Optimistic label timing and current-vintage data

Training uses outcomes not yet observable in Jan 2015 (see the embargo experiment). FRED series are today's revised values, not the first releases a lender would have seen.

Run it

  1. Installpip install -r requirements.txt (Python 3.12)
  2. Download loansKaggle wordsforthewise/lending-club → data/raw/microdata.csv, then python src/microdatafilterscript.py
  3. Download macro dataPut FRED_API_KEY in .env, then python src/build_macrodata.py
  4. Runmacro_stress_testing.ipynb top to bottom (~10 min). It rewrites every table, figure and this site's data file.

Where things are

  • macro_stress_testing.ipynb: full pipeline with outputs
  • src/: data build, lag/merge, leakage checks, censoring audit
  • src/config.py: splits, feature groups, grids, seeds
  • reports/results/: every result table as CSV
  • predict.py: command-line scoring with the saved models
